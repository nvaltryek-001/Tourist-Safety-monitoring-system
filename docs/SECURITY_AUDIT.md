# Security and privacy audit

Scope: backend, dashboard, mobile app, configuration. Date: 2026-11-01.

## Findings in the original code and their fixes
| # | Severity | Finding (before) | Fix |
|---|---|---|---|
| 1 | Critical | `GET /tourists` was public and returned names, phones, emails, emergency contacts and live coordinates of every tourist | admin-only; staff list masks contacts for police |
| 2 | Critical | `POST /tourists/{code}/location` and `/sos` were unauthenticated — anyone could move a tourist or raise SOS as them | bearer token required; tourists may act only on themselves |
| 3 | High | `GET /sos` public (locations of emergencies) | staff-only |
| 4 | High | `POST /tourists`, `POST /zones` public | admin-only, audit-logged |
| 5 | High | A personal Gmail address was hard-coded as the default SOS alert recipient in `main.py` | removed; `ADMIN_ALERT_EMAIL` env var with empty default |
| 6 | Medium | No authentication, roles, sessions or audit trail at all | JWT + server-side sessions, 4 roles, audit log |
| 7 | Medium | No rate limits | OTP, verify, staff login, location and SOS rate limits |
| 8 | Medium | Notification code reported provider acceptance ambiguously | explicit `ACCEPTED_BY_PROVIDER` / `FAILED` / `NOT_CONFIGURED` |

Note: the old public endpoints remain reachable on any copy of the **old** code that is still running. Redeploy from this version.

## Checklist
| Area | Status |
|---|---|
| Authentication bypass | every personal-data route depends on `get_principal`; session row checked on each request and on WebSocket connect; tests cover 401/403 boundaries |
| Broken authorization | tourist ↔ tourist isolation (`/me/*`, SOS 404 for others), police case isolation, admin-only management, super-admin-only admin changes |
| SQL injection | SQLAlchemy ORM / bound parameters only; the only raw SQL is fixed identifiers in the migrator |
| XSS | React escapes output; no `dangerouslySetInnerHTML`; the `/register` page uses `textContent` |
| CSRF | tokens are sent as `Authorization` headers, not cookies, so cross-site forms cannot use them |
| File uploads | GeoJSON/KML only, 5 MB and 5 000-feature limits, DTD/ENTITY KML rejected, never written to disk, dry-run first |
| Sensitive data exposure | masked contacts for police, no PII in logs/audit details, OTPs stored as HMAC, passwords PBKDF2 |
| Location retention | 30-day default, admin purge, tourist self-delete, consent required before any upload |
| Session handling | revocable `jti`, logout, per-device revoke, password change revokes others, 12 h staff / 7 d tourist expiry |
| Secrets | none committed; `SECRET_KEY` generated by Render; app refuses to start in production with the dev key or < 32 chars |
| CORS | explicit `ALLOWED_ORIGINS`; credentials disabled |
| Debug mode | no debug flags; generic 500 responses; structured logs |
| Security headers | API: nosniff, no-referrer, DENY framing; dashboard: same + Permissions-Policy |
| Dependency vulnerabilities | not scanned in this session (package registry access was unavailable locally); run `pip-audit` and `npm audit` in CI before production |
| Demo credentials | public in README by request; created only with `SEED_DEMO_STAFF=true` and never in production |
| `OTP_DEV_ECHO` | must stay `false` in production: with it on, anyone who knows an approved Gmail can sign in as that tourist |

## Residual risks
* Rate limiting and WebSocket fan-out are per-process (fine for one Render instance).
* Tokens in the dashboard live in `localStorage`; an XSS would expose them (mitigated by React escaping and no third-party scripts besides map tiles).
* No 2FA for staff.

No critical or high findings remain open in the code reviewed.
